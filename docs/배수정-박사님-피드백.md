## 피드백 해석 및 개선 방향

### 1. "뒤에서부터 접근" — ABSA 분류 결과 검증

**의미**: Claude가 내린 sentiment 분류가 실제로 맞는지 사람이 검증해야 한다는 뜻.
예: "바쁘셔서 질문하기 어려울 때가 있었어요" → `약간부정` 분류가 적절한지 확인 필요.

**현재 상태**: Claude zero-shot 분류 결과를 검증 없이 그대로 사용 중.

**개선안**:
- 분석 결과 20~30건을 HR 담당자가 직접 리뷰해서 "골드 셋" 구축
- 잘못 분류된 케이스를 모아 프롬프트 개선에 반영

---

### 2. "5단계 + 점수화" — 감성 구간별 대응 차등화

**의미**: 현재 5단계 sentiment 분류는 충분하지만, `sentiment_score`를 구간으로 묶어 대응 수준을 다르게 하라는 뜻.

**제안 구조**:

| 구간 | 점수 범위 | 대응 |
|------|----------|------|
| Green | 0.5 ~ 1.0 | 멘토에게 격려 메일만 |
| Yellow | -0.2 ~ 0.5 | 멘토 가이드 메일 + 팀장 공유 |
| Red | -1.0 ~ -0.2 | HR 직접 면담 개입 알림 |

현재 `sentiment_score` 필드가 이미 존재하므로, 이메일 생성 시 톤 자동 조절 또는 HR 개입 알림 추가로 확장 가능.

---

### 3. "앞에서부터 접근" — 전처리 단계 룰 기반 문장 분리

**의미**: `~지만`, `~하지만`, `~이기는한데`, `~긴 하지만` 같은 양보/전환 접속어가 포함된 복합 문장을 **Claude에 넘기기 전에** 룰 기반으로 분리하라는 뜻.

**문제 현황**: 복합 감성 문장이 통째로 처리되면 sentiment가 중립으로 뭉개질 수 있음.

**개선 예시**:
```
원문: "멘토가 친절하시지만 피드백 주기가 늦어서 답답했어요"
→ 분리 후:
  - "멘토가 친절하시다" → 긍정
  - "피드백 주기가 늦어서 답답했다" → 부정
```

**접근 방식**: Python/JS 룰 기반으로 접속어 패턴을 찾아 문장 분리 → 각 조각을 LLM에 전달.

---

### 4. "Claude Code 세션 내 에이전트 분석 + Few-shot 구축"

**두 가지 포인트**:

**4a. 비용 절감**
매번 Edge Function → Claude API 호출 대신, Claude Code 세션에서 HR 담당자가 직접 분석을 돌려볼 수 있게 하면 API 비용 없이 동일한 분석 가능.

**4b. Few-shot 구축 프로세스**
1. 기존 설문 데이터를 Claude Code 세션에서 분석
2. 잘 분류된 결과를 선별 (= 골드 셋)
3. 해당 결과를 프롬프트 few-shot 예시로 포함

**현재**: zero-shot (예시 없이 지시만)
**개선 후**: few-shot (검증된 예시 2~3개 포함)

```
예시 1:
입력: "피드백을 빠르게 주셔서 좋았어요"
출력: {"aspect":"피드백 응답 속도","sentiment":"긍정","score":0.85}

예시 2:
입력: "잘 해주시긴 하는데 가끔 바쁘실 때 연락이 안 돼요"
출력: [
  {"aspect":"멘토링 전반 만족도","sentiment":"긍정","score":0.6},
  {"aspect":"멘토 가용성","sentiment":"약간부정","score":-0.4}
]
```

---

### 5. "Aspect 중분류/대분류 사전 구축"

**의미**: 현재 aspect 이름이 Claude가 자유롭게 생성 (예: "멘토의 피드백 빈도", "피드백 주기", "피드백 속도" — 다 다른 이름이지만 같은 개념). 체계적인 분류 체계(사전)로 관리하라는 뜻.

**예시 구조**:
```
대분류: 멘토링 역량
  중분류: 피드백
    소분류(aspect): 피드백 빈도, 피드백 품질, 피드백 속도
  중분류: 소통
    소분류: 가용성, 경청, 심리적 안전감

대분류: 조직 적응
  중분류: 업무 이해
    소분류: 업무 범위 안내, 역할 명확성
  중분류: 관계 형성
    소분류: 팀 소개, 네트워킹 지원
```

**이 구조가 가능하게 하는 것**:
- 여러 명의 설문을 대분류/중분류 단위로 집계
- 멘토 간 비교, 차수별 시계열 추적
- 멘토 점수화 및 군집 분석의 기반

---

### 6. "신뢰도 기준 명확화" + 멘토 프로파일링/군집 분석

**현재 문제**: `confidence: "높음/보통/낮음"` — Claude 자체 판단이라 기준이 불투명하고 UI에서 사용자가 해석하기 어려움.

**개선안**: 신뢰도 대신 근거 기반 표현으로 전환
- "높음" → "원문에서 명시적 표현 확인됨"
- "보통" → "문맥에서 추론됨"
- "낮음" → "간접적 언급, 해석 여지 있음"

**멘토 프로파일링 (장기 목표)**:
- 각 멘토에 대한 aspect 점수 집계 → 멘토 종합 점수 산출
- K-means로 "멘티가 좋아한 멘토 행동 패턴" 군집화
- 우수 멘토의 행동 패턴 → 멘토 가이드북 자동 생성

## 우선순위 제안

| 순위 | 작업 | 난이도 | 효과 |
|------|------|--------|------|
| 1 | Few-shot 예시 구축 (기존 데이터 분석 → 골드셋) | 낮음 | 높음 |
| 2 | 룰 기반 전처리 (양보/전환 접속어 분리) | 중간 | 높음 |
| 3 | Aspect 분류 사전 초안 작성 | 중간 | 높음 |
| 4 | 신뢰도 기준 명확화 + UI 개선 | 낮음 | 중간 |
| 5 | 점수 구간별 대응 차등화 | 낮음 | 중간 |
| 6 | 멘토 프로파일링 / K-means 군집 분석 | 높음 | 높음 (장기) |

### 논의 결론

**문제**: Claude가 이메일 본문 생성 시 `**굵게**`, `##제목` 같은 마크다운 기호를 간헐적으로 포함시킴.

**검토한 해결 방법**:
1. **프롬프트 강화**: 출력 규칙에 마크다운 기호 금지 한 줄 추가 (`**, ##, >, `, _ 금지`)
2. **HTML 변환**: Edge Function에서 body를 HTML로 변환 후 저장, UI에서 HTML 렌더링

**결론: 프롬프트 강화만 필요 (HTML 변환은 불필요)**

현재 워크플로우가 "생성된 메일 복사 → 그룹웨어 이메일 에디터에 붙여넣기"이므로, HTML로 변환하면 오히려 `<p>`, `<br>`, `<ul>` 같은 태그가 그대로 텍스트로 붙여넣어지는 역효과 발생.

**조치 방향**: `generate-email/index.ts` 프롬프트 `[출력 규칙]` 섹션에 아래 한 줄 추가 (보류 중)
```
- **, ##, >, `, _ 같은 마크다운 기호를 절대 사용하지 마십시오.
```
