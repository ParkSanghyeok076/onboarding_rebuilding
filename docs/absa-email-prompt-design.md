# 이메일 생성 프롬프트 설계 고민 (2026-03-23)

> 파일: `supabase/functions/generate-email/index.ts`
> 현재 상태 진단 + 개선 방향 정리

---

## 1. 현재 구조 평가

### 잘 설계된 부분

- 멘토/팀장 구분
- 신입/경력 구분
- 제목·인사말·문의 문구 고정
- 금지어 치환 (`설문` → `정기 체크인` 등)
- 본문만 JSON으로 생성 (`body` 필드)

### 현재의 한계

`analysisResult.aspects` 전체를 그대로 넣고 톤 가이드 중심으로 메일을 생성하는 구조라,
아래 세 가지가 프롬프트에서 충분히 통제되지 않는다.

1. **누가 해결해야 하는 이슈인지** (owner 배정)
2. **무엇을 우선 강조해야 하는지** (우선순위 필터링)
3. **반복 신호를 어떻게 해석할지** (반복 → 핵심 미충족 욕구)

> 즉, 지금 메일 프롬프트는 **"예쁘게 쓰기"는 되지만, "정확하게 넛지하기"는 약한 구조**.

### ABSA 개선과의 연계 문제

변경된 ABSA 프롬프트는 이메일 생성 활용도는 높였지만,
과세분화된 속성이 그대로 후속 단계로 넘어갈 경우:

- 멘토 이슈와 조직 적응 이슈가 한 메일에 섞여 수신자가 "내가 뭘 하면 되지?"를 잡기 어려워짐
- 원인-결과를 둘 다 따로 메일에 실으면 장황해짐

## 2. 핵심 원칙

**수신자별 역할 책임(owner)에 맞게 다른 정보를 다른 형식으로 전달.**

| 수신자 | 포커스 | 형식 |
|--------|--------|------|
| **멘토** | 정서적 부담 없이 바로 행동할 수 있는 관계/멘토링 넛지 1~2개 | 3~4문단 서술형 |
| **팀장** | 팀 적응·업무환경·조직 지원 차원의 관찰 포인트 | 한 줄 요약 + 불렛 리포트 |

같은 ABSA 결과를 쓰더라도 **메일에 들어가는 정보는 달라야 한다**.

---

## 3. 멘토 메일 설계

### 포함 요소 4가지

**① 강점 1개 (먼저)**

- 두루뭉술한 감사 표현 금지
- ABSA에서 `confidence = 높음` + `quote` 근거가 분명한 긍정 항목 1개만 선택
- 수신자가 "내가 뭘 유지하면 되는지"를 즉시 파악하게

예시 대상 속성:
- 질문을 편하게 할 수 있게 해주는 분위기
- 바로바로 알려주는 응답 속도
- 바쁜 중에도 시간을 내주는 헌신성

**② 보완 포인트 1개만**

- ABSA 결과를 여러 개 넣으면 멘토가 방어적으로 읽음
- 선택 기준:
  - `owner = mentor`
  - `sentiment = 약간부정 | 부정`
  - `confidence = 높음` 우선
  - 여러 field에서 반복 등장하면 우선순위 상승

예시 대상 속성:
- 자율적 업무 시도 기회 부족
- 업무 외 비공식 소통 부족

**③ 행동 제안은 구체적으로**

"조금 더 신경 써 주세요" 수준이 아닌, **다음 1~2주 안에 실천 가능한 행동**으로 제시.

예시:
- 설명 후 바로 답을 주기보다, 먼저 신입이 한 번 시도해보게 한 뒤 확인해 주기
- 주 1회 10분 정도 업무 외 대화 시간 갖기
- 동료와 자연스럽게 연결될 수 있도록 점심/짧은 소개 자리 마련하기

**④ 관찰 근거는 완곡한 요약으로**

- 원문 quote 직접 인용 금지 → 수신자가 "감시받는다"는 느낌을 받을 수 있음
- 대신 한 줄 요약 근거로 전환:
  - "최근 체크인 과정에서"
  - "적응 초기에"
  - "업무 이해는 빠르지만, 스스로 해보는 기회를 더 원한다는 신호가 있어"

### 권장 구조

```
1문단: 감사 + 강점 1개
2문단: 최근 관찰된 포인트 1개
3문단: 바로 실천 가능한 제안 1~2개
4문단: 응원/감사
```

### 예시 본문

```
OO님, 안녕하세요.

최근 체크인 과정에서 신규 입사자가 업무 관련 질문을 편하게 드릴 수 있었고,
필요한 안내도 빠르게 받을 수 있었다는 긍정적인 신호가 확인되었습니다.
초기 적응에 큰 도움이 되고 있는 점 감사드립니다.

한편, 업무를 이해하는 과정에서는 충분한 안내를 받고 있으나,
스스로 한 번 시도해 보고 점검받는 기회가 조금 더 있으면 좋겠다는 흐름도 함께 보였습니다.

가능하시다면 앞으로는 설명 후 바로 답을 주시기보다, 작은 업무 단위에서는 먼저 시도해 볼
시간을 드린 뒤 확인해 주시는 방식도 도움이 될 수 있겠습니다. 또 짧게라도 업무 외 이야기를
나눌 수 있는 시간을 한 번씩 가져 주시면 심리적 안정감 형성에 도움이 될 것 같습니다.

항상 세심하게 멘토링해 주셔서 감사드리며, 앞으로의 멘토링도 잘 이어질 수 있도록 응원하겠습니다.
```

> 장점: 평가/지적 느낌이 약하고, 행동 유도가 명확함.

## 4. 팀장 메일 설계

### 포함 요소 4가지

**① 전반 상태 한 줄 (리드 문장)**

팀장이 메일의 핵심을 5초 안에 이해하게 하는 한 줄.

예시:
- "전반적으로 초기 적응은 안정적이나, 비공식 소통과 팀 내 연결 측면에서 보완 신호가 확인됨"
- "업무 안내와 반응 속도는 긍정적이나, 업무 자율성과 네트워킹 측면의 보완 필요"

**② 팀장 관점의 이슈만 추림**

`owner = team | organization | environment | program` 중심 항목 우선.

포함 대상 예시:
- 동료 네트워킹 지원
- 팀 내 비공식 적응
- 사무 비품/업무환경 지원
- 멘토링 예산 운용 유연성
- 초기 업무 설계 상 자율성 수준

`owner = mentor`인 세부 대화 스타일 문제는 팀장 메일에 길게 쓰지 않음.
→ 들어가더라도 "멘토링 운영 차원에서 함께 살펴봐 주시면 좋겠습니다" 정도.

**③ 조치 포인트는 "지원 요청" 언어로**

지적보다 지원 요청이 적절:
- "초기 적응을 위해 동료 소개나 자연스러운 접점 형성을 한 번 지원해 주시면 좋겠습니다."
- "소모성 비품이나 기본 업무 환경은 팀 차원에서 점검이 필요해 보입니다."

**④ HR이 처리할 사안은 팀장에게 떠넘기지 않기**

예산 이월, 제도, 프로그램 설계 등:
- "팀장님이 해결" → `"운영상 참고가 필요한 이슈"` 또는 `"HR에서 함께 검토하겠습니다"`로 표현.

### 권장 구조

```
한 줄 상태 요약
- 강점 유지 포인트
- 관찰된 보완 포인트
- 팀장 지원 제안
마무리: HR 협업/응원 문구
```

### 예시 본문

```
팀장님, 안녕하세요.

최근 1개월차 정기 체크인 내용을 보면, 초기 업무 적응은 전반적으로 안정적인 편이나
팀 내 비공식 소통과 연결 측면에서 보완 신호가 일부 확인되었습니다.

- 강점 유지
  업무 관련 안내와 의견 수렴 경험은 긍정적으로 인식되고 있습니다.
  특히 초기에 질문이 가능한 분위기와 빠른 안내는 적응에 도움이 된 것으로 보입니다.

- 관찰 포인트
  업무 외적인 대화나 주변 동료와의 자연스러운 연결은 다소 부족하게 느끼는 흐름이 있었습니다.
  또한 일부 환경 지원 항목은 실무 적응 과정에서 불편으로 이어질 가능성이 있어 보입니다.

- 팀 차원 제안
  초기에 함께 일하는 구성원을 자연스럽게 소개받을 수 있는 기회를 한 번 마련해 주시고,
  소모성 비품이나 기본 업무 환경도 간단히 점검해 주시면 적응 안정화에 도움이 될 것 같습니다.

신규 입사자의 안착을 위해 팀장님의 관심과 지원이 큰 역할을 하고 있어,
가능한 범위에서 함께 살펴봐 주시면 감사하겠습니다.
```

## 5. 프롬프트에 추가할 규칙

현재 `index.ts`는 `analysisResult.aspects` 전체를 그대로 넣고 있음.
→ 모델이 중요하지 않은 속성을 길게 풀거나, recipient와 맞지 않는 이슈를 넣을 가능성 있음.

### 공통 규칙

1. 최대 1개 강점 + 최대 2개 보완 포인트만 사용
2. 반복 등장한 항목은 우선순위를 높게 반영
3. `confidence = 낮음` 항목은 단정적으로 쓰지 말 것
4. `quote`를 직접 인용하지 말고 요약 표현으로 전환
5. recipient가 통제할 수 없는 항목은 "참고/협업 필요"로 표현

### 멘토용 추가 규칙

1. `owner = mentor` 중심으로 선택
2. 보완 포인트는 1개만 핵심으로 제시
3. 실천 행동은 1~2개까지만
4. 평가/지적 문장보다 관계적 제안 문장 우선

### 팀장용 추가 규칙

1. `owner = team | organization | environment | program` 우선
2. 팀 운영/업무환경/적응 지원 이슈 중심으로 묶기
3. 분포 숫자보다 상태 요약 우선
4. 개인 비판으로 읽히지 않게 팀 차원의 지원 언어 사용

## 6. 중간 요약 객체 도입 제안

ABSA 결과를 그대로 메일 생성에 넣지 않고, **한 번 더 요약하는 중간 단계** 권장.
ABSA 과세분화의 부작용이 메일 문장으로 번지는 것을 막는 완충 역할.

### 멘토용 요약 객체

```json
{
  "recipient_type": "mentor",
  "employee_type": "신입",
  "overall_status": "초기 적응은 안정적이나 자율적 시도 기회에 대한 욕구가 관찰됨",
  "top_strength": {
    "aspect": "질문 수용성과 피드백 신속성",
    "sentiment": "긍정",
    "confidence": "높음"
  },
  "top_nudge": {
    "aspect": "자율적 업무 시도 기회",
    "sentiment": "약간부정",
    "confidence": "높음",
    "repeated": false
  },
  "suggested_actions": [
    "설명 후 먼저 시도해볼 시간을 주기",
    "작은 단위 업무를 맡기고 이후 함께 점검하기"
  ]
}
```

### 팀장용 요약 객체

```json
{
  "recipient_type": "team_leader",
  "employee_type": "신입",
  "overall_status": "전반 적응은 안정적이나 네트워킹 및 환경 지원 보완 필요",
  "strengths": [
    "초기 업무 안내 경험은 긍정적"
  ],
  "watch_points": [
    "동료 네트워킹 지원",
    "사무 비품 지원"
  ],
  "team_actions": [
    "동료 소개 및 자연스러운 접점 마련",
    "기본 업무환경 점검"
  ],
  "hr_followup": [
    "멘토링 예산 운용 관련 제도 검토"
  ]
}
```

## 7. Few-Shot 메일 단계에도 적용

ABSA만 few-shot을 쓰고 메일은 zero-shot으로 두면 후속 생성 품질이 흔들릴 수 있음.
**3개 정도면 충분**, 길지 않게 `입력 요약 객체 → 출력 메일 본문` 형태로 구성.

| 케이스 | 내용 |
|--------|------|
| 예시 1 | 멘토용 / 강점 + 완곡한 보완 1개 |
| 예시 2 | 멘토용 / 역설 표현 처리 ("너무 잘 알려주시는 게 문제" → 자율성 기회 제안) |
| 예시 3 | 팀장용 / 팀 적응 + 환경 지원 이슈 (네트워킹, 비품, 온보딩 환경) |

---

## 8. 가장 먼저 바꿀 것

> **`analysisResult.aspects` 전체를 넣지 말고, 수신자 기준으로 1차 필터링·요약한 뒤 메일 생성에 넣기.**

이 한 가지만 해도:
- 멘토 메일이 덜 장황해지고
- 팀장 메일이 더 운영적이 되며
- 잘못된 책임 배정이 줄고
- 넛지다운 느낌이 훨씬 강해짐
