## 1. 프롬프트 비교

### 기존 프롬프트

```
아래는 신입사원의 온보딩 설문 주관식 응답입니다.
각 파트는 응답의 맥락 구분용입니다.
속성명은 파트명을 그대로 쓰지 말고, 텍스트에서 드러난 실제 개념으로 추출하세요.
응답이 없거나 '-', '없음'인 항목은 분석에서 제외하세요.

[멘토링 태도] {q1_5}
[업무 지식 전수] {q2_5}
[실무 피드백] {q3_5}
[조직 적응 지원] {q4_5}
[강점/유지] {q5_1}
[개선 제안] {q5_2}
[자유 의견] {q5_3}

반드시 아래 JSON 형식으로만 반환하세요:
[{"aspect":"실제 개념명","sentiment":"긍정|약간긍정|중립|약간부정|부정","sentiment_score":-1.0,"confidence":"높음|보통|낮음","quote":"원문 발췌","source_field":"q1_5"}]
```

### 변경 프롬프트

```
당신은 인적 자원 관리(HRM) 및 개발(HRD) 전문가이자 숙련된 데이터 분석가입니다.
신입사원의 온보딩 설문 응답을 분석하여, 각 응답에 담긴 세부 속성(Aspect)과 그에 대한
감성(Sentiment)을 추출하십시오.

[분석 지침]
1. 중간 추론(Reasoning) 포함: 각 속성을 도출하기 전, 응답자가 어떤 맥락에서 해당
   표현을 사용했는지 짧게 추론하십시오. 이는 분석의 정확도를 높이는 데 필수적입니다.
2. 속성명 구체화: '멘토링 태도' 같은 파트명을 그대로 쓰지 마십시오. 대신 '피드백의
   구체성', '정서적 지지', '업무 지식의 전문성', '응답 속도' 등 실제 언급된 개념으로
   구체화하십시오.
3. 감성 판단 기준:
   - '중립'은 감정이 배제된 단순 사실 나열이나 판단 유보인 경우에만 부여하십시오.
   - 약간긍정/약간부정은 태도는 보이나 강도가 약할 때 사용합니다.
4. 다중 속성 추출: 한 문장에 여러 속성이 포함된 경우, 각각 분리하여 분석하십시오.
5. 필터링: 내용이 없거나 '-', '없음', '모르겠음' 등 유의미한 정보가 없는 경우는
   JSON 결과에서 제외하십시오.

[입력 데이터]
- 멘토링 태도: {q1_5}
- 업무 지식 전수: {q2_5}
- 실무 피드백: {q3_5}
- 조직 적응 지원: {q4_5}
- 강점/유지: {q5_1}
- 개선 제안: {q5_2}
- 자유 의견: {q5_3}

[출력 형식]
반드시 아래의 JSON 구조로만 응답하십시오. (다른 텍스트는 금지)
[
  {
    "source_field": "q1_5",
    "reasoning": "응답자가 멘토의 태도에 대해 ~라고 언급한 것은 ~에 대한 만족감을 나타냄",
    "aspect": "실제 개념명",
    "sentiment": "긍정|약간긍정|중립|약간부정|부정",
    "sentiment_score": -1.0에서 1.0 사이의 실수,
    "confidence": "높음|보통|낮음",
    "quote": "분석의 근거가 된 원문 발췌"
  }
]
```

## 2. 프롬프트 구조 비교

| 항목 | 기존 프롬프트 | 변경 프롬프트 |
|---|---|---|
| **역할 부여** | 없음 | HRM/HRD 전문가 + 데이터 분석가 |
| **분석 지침** | 2줄 (암묵적) | 5개 명시적 항목 |
| **Reasoning 필드** | 없음 | 필수 포함 |
| **다중 속성 추출** | 명시 없음 (파트당 1개 경향) | 명시적으로 지시 |
| **감성 중립 기준** | 없음 | 명확한 판단 기준 제시 |
| **역설 표현 처리** | 처리 안 됨 | Reasoning으로 맥락 파악 가능 |
| **출력 필드 수** | 6개 | 7개 (reasoning 추가) |

## 9. Few-Shot 설계 및 프롬프트 개선안 (2026-03-23)

> 업로드된 MD와 두 논문(패션 리뷰, 휴대폰 리뷰 대상 한국어 ABSA)을 바탕으로 정리.
> 논문 결과를 온보딩/멘토링 서술형 응답 도메인으로 전이 적용한 설계안이므로,
> 바로 운영 적용보다 작은 gold set으로 A/B 테스트하는 방식을 권장.

---

### 9-1. 핵심 인사이트 (논문 결과 요약)

- **출력 형식은 짧고 구조적일수록 유리.** 긴 reasoning chain(THOR류)은 오히려 성능을 떨어뜨림. 짧은 중간 추론(CoT)은 도움이 될 수 있음.
- **예시 수보다 예시의 설계 품질이 중요.** GPT-4o-mini 기준 few-shot이 zero-shot·one-shot보다 약간 나았지만 개선 폭은 크지 않음. 가장 큰 성능 향상은 fine-tuning에서 나옴.
- **한국어 ABSA 정확도 저하 주요 원인:** 주어/목적어 생략, 같은 속성의 다양한 표현, 완곡·간접 표현, 이중 부정, 애매한 중립 표현.
  - 온보딩/멘토링 서술형도 도메인은 다르지만 한국어 특성은 동일하게 나타남.
  - 예: "좋기는 한데…", "문제라면 너무 잘 알려주신다", "좀 아쉽지만…"
- **기존 MD의 핵심 빈칸:** 변경 프롬프트는 완전성·역설 표현 처리·근거 추적성은 개선됐으나, **통합 기준이 없어 원인-결과까지 과세분화**되는 문제가 미해결.
- **few-shot 예시 전략:** "대표 응답"이 아니라 **"실패하기 쉬운 경계 사례"** 중심으로 구성.

---

### 9-2. 추천 개선 방향 (4가지 핵심)

| # | 개선 항목 | 내용 |
|---|-----------|------|
| 1 | **few-shot 예시 선정** | 역설 표현, 유보적 긍정, 간접 부정, 원인-결과 통합 사례, 해결 주체가 달라 분리해야 하는 사례 |
| 2 | **reasoning 최소화** | 긴 explanation 대신 `rationale_short` 한 줄. 운영 환경에서는 reasoning 없이, 튜닝/검증 환경에서만 출력 |
| 3 | **분리 규칙 + 통합 규칙 동시 명시** | 현재 MD의 가장 큰 빈칸 |
| 4 | **`sentiment_score` 후처리 매핑** | 모델이 free-form 실수값을 생성하지 않도록, 라벨 → 점수 매핑을 후처리로 처리 (긍정=1, 약간긍정=0.5, 중립=0, 약간부정=-0.5, 부정=-1) |

---

### 9-3. 권장 프롬프트 구조 (v3 초안)

```
당신은 HRD/온보딩 경험 분석 전문가입니다.
목표는 신입사원의 온보딩/멘토링 서술형 응답에서 독립적이고 실행 가능한 경험 요인(aspect)과
그 감성(sentiment)을 추출하는 것입니다.

[작업 정의]
- aspect는 응답자가 평가하는 "독립적 경험 요인"입니다.
- 설문 파트명(예: 멘토링 태도, 조직 적응 지원)을 그대로 aspect로 쓰지 마십시오.
- 반드시 실제 응답에서 드러난 개념으로 정제하십시오.
  예: 피드백의 신속성, 자율적 업무 시도 기회, 동료 네트워킹 지원, 비공식 소통, 예산 운용 유연성

[한국어 해석 원칙]
- 생략된 주어/목적어는 문맥으로 복원하십시오.
- 완곡 표현, 역설 표현, 이중 부정, 유보적 긍정에 주의하십시오.
- "나쁘지 않다", "그저 그렇다", "애매하다", "좀 아쉽다", "~같기는 하다"는
  앞뒤 문맥을 함께 보고 판단하십시오.

[분리 규칙]
아래 조건 중 하나라도 만족하면 aspect를 분리하십시오.
1. 해결 주체(owner)가 다르다.
   - 예: mentor 문제 vs organization/program 문제
2. 서로 독립적인 개선 액션이 필요하다.
3. 동일 문장 안에 서로 다른 평가 대상이 병렬로 언급된다.

[통합 규칙]
아래 조건이면 하나의 aspect로 통합하십시오.
1. 원인-결과 관계다.
   - 예: "시간을 내어 알려줘서 빠르게 파악했다"
2. 동일 행동을 다른 각도에서 다시 표현한 것이다.
   - 예: "질문하라고 해주셨고 바로 답을 주셨다"
3. 같은 뿌리의 문제에서 나온 파생 효과다.
   - 예: "스스로 해볼 기회가 부족해서 이해도 점검이 어렵다"

[감성 기준]
- 긍정: 명확한 만족/칭찬
- 약간긍정: 유보적 인정, 약한 호감
- 중립: 사실 서술, 판단 유보, 감정이 거의 없음
- 약간부정: 아쉬움, 완곡한 불만, 개선 희망
- 부정: 명시적 불만, 강한 문제 제기

[출력 원칙]
- quote는 반드시 원문 그대로의 최소 근거 구절만 사용하십시오.
```

### 9-5. 운영 구조 권장 — 1프롬프트 2단계

| 단계 | 역할 | 프롬프트 |
|------|------|----------|
| **1단계** | mention-level 추출 (놓치지 않고 뽑기) | 위 v3 프롬프트 + few-shot |
| **2단계** | consolidation (중복 aspect 병합, 우선순위 정리) | 별도 consolidation prompt |

> 1단계에서 과세분화를 허용하고, 2단계에서 줄이는 구조.
> 현재 MD의 과세분화 고민이 이 구조에서 자연스럽게 해결됨.

### 9-6. 검증 방법 (gold set A/B 테스트)

> exact match만 보면 억울한 오답이 생길 수 있어, 정답 기준 평가 + 전문가 검토/G-Eval류 보완 평가를 병행 권장.

**권장 체크 항목 4개:**

- [ ] aspect exact match
- [ ] sentiment F1
- [ ] 과세분화율
- [ ] 허위 aspect 비율 (spurious aspect)

### 9-7. `sentiment_score` 후처리 매핑 (코드)

모델이 free-form 실수값을 직접 생성하면 오류가 많으므로, 감성 라벨 → 점수 변환을 후처리로 처리:

```javascript
const SENTIMENT_SCORE_MAP = {
  '긍정': 1.0,
  '약간긍정': 0.5,
  '중립': 0.0,
  '약간부정': -0.5,
  '부정': -1.0,
}

// aspects 파싱 후 적용
aspects = aspects.map(a => ({
  ...a,
  sentiment_score: SENTIMENT_SCORE_MAP[a.sentiment] ?? 0,
}))
```
